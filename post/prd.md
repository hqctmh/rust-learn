# Leptos 全栈技术论坛项目需求列表

## 1. 项目目标

新增一个基于 **Leptos 全栈模式** 的技术论坛项目，目标是实现一个类似掘金的技术社区系统，包含用户端和管理端。

系统需要支持文章发布、Markdown 编辑、图片上传、评论回复、点赞、关注、消息推送、公告推送、搜索、内容管理、权限控制等常见论坛能力。

## 2. 技术选型

### 2.1 前后端框架

* 前端/全栈框架：Leptos
* 后端服务：Rust
* UI 组件/样式：DaisyUI
* 实时通信：WebSocket
* Markdown 编辑器：支持 Markdown 编辑、预览、图片上传、代码块高亮

### 2.2 基础设施

* 数据库：PostgreSQL
* 缓存：Redis
* 消息队列/事件总线：NATS
* 对象存储：RustFS，用于图片、附件等文件存储
* 搜索引擎：Elasticsearch
* 本地开发环境：Docker Compose

### 2.3 建议职责划分

* PostgreSQL：核心业务数据存储
* Redis：缓存、限流、热点数据、会话状态、临时验证码、计数缓存
* NATS：用户通知、关注推送、公告推送、搜索索引异步更新等事件分发
* RustFS：帖子图片、用户头像、公告图片、附件存储
* Elasticsearch：帖子搜索、用户搜索、标签搜索、全文检索

首页需要包含：

* 搜索入口

帖子列表需要展示：

* 分类

列表需要支持：

* 分页或无限滚动
* 按时间排序

* 按分类过滤
* 按标签过滤

## 4.2 帖子发布与编辑

用户登录后可以发布帖子。

帖子字段包括：

* 标题
* Markdown 正文
* 封面图，可选
* 分类
* 标签
* 摘要，可自动生成，也可手动填写
* 是否发布
* 是否保存为草稿

编辑器要求：

* 使用 Markdown 格式编辑
* 支持实时预览
* 支持上传图片
* 上传图片后自动插入 Markdown 图片链接
* 支持代码块
* 支持代码高亮
* 支持表格
* 支持引用
* 支持有序列表、无序列表
* 支持撤销、重做
* 支持草稿自动保存

安全要求：

* Markdown 渲染后的 HTML 必须做 XSS 过滤
* 图片上传需要限制文件类型
* 图片上传需要限制文件大小
* 用户只能编辑、删除自己的帖子
* 管理员可以下架或删除违规帖子

## 4.3 帖子详情

帖子详情页需要展示：

* 标题
* 作者信息
* 发布时间
* 更新时间
* 分类
* 标签
* Markdown 渲染后的正文
* 浏览数
* 点赞数
* 收藏数
* 评论数
* 评论列表
* 相关推荐帖子

登录用户可以：

* 点喜欢 / 取消喜欢
* 收藏 / 取消收藏
* 关注作者 / 取消关注
* 发表评论
* 回复评论
* 举报帖子

未登录用户可以：

* 查看帖子内容
* 查看评论
* 点击登录后再进行互动操作

## 4.4 评论与回复

帖子支持评论，评论支持回复。

评论功能包括：

* 一级评论
* 二级回复
* 评论点赞
* 评论删除
* 评论举报
* 作者回复标识
* 管理员删除违规评论

评论权限：

* 未登录用户只能查看评论
* 登录用户可以发表评论和回复
* 用户可以删除自己的评论
* 管理员可以删除任意评论
* 被删除评论需要保留占位提示，例如“该评论已被删除”

## 4.5 点喜欢

帖子支持喜欢功能。

要求：

* 登录用户可以点喜欢
* 登录用户可以取消喜欢
* 同一用户对同一帖子只能喜欢一次
* 喜欢数需要展示在帖子列表和详情页
* 点喜欢后需要通知帖子作者
* 高频计数可以使用 Redis 缓存，最终数据落 PostgreSQL

## 4.6 收藏

建议补充收藏功能。

要求：

* 登录用户可以收藏帖子
* 登录用户可以取消收藏
* 用户可以查看自己的收藏列表
* 同一用户对同一帖子只能收藏一次

## 4.7 关注

用户之间可以关注。

要求：

* 登录用户可以关注其他用户
* 登录用户可以取消关注
* 用户不能关注自己
* 用户主页展示关注数和粉丝数
* 用户可以查看关注列表
* 用户可以查看粉丝列表
* 被关注用户发布新帖子后，需要给关注者发送通知

## 4.8 通知与推送

系统需要支持站内通知和 WebSocket 实时推送。

通知类型包括：

* 关注用户发布新帖子
* 帖子被评论
* 评论被回复
* 帖子被喜欢
* 评论被喜欢
* 系统公告
* 管理员通知

通知要求：

* 登录后建立 WebSocket 连接
* 新通知通过 WebSocket 实时推送
* 用户可以查看历史通知
* 用户可以标记单条通知已读
* 用户可以全部标记已读
* 未在线用户的通知需要持久化
* 用户重新上线后可以拉取未读通知

推荐流程：

* 业务操作产生事件
* 事件发送到 NATS
* 通知消费者处理事件
* 通知写入 PostgreSQL
* 在线用户通过 WebSocket 推送
* 未在线用户下次登录后拉取未读通知

搜索范围包括：

* 帖子标题

* 按时间排序
* 按热度排序

Elasticsearch 索引更新要求：

* 帖子删除或下架后从搜索结果中移除
* 可以通过 NATS 异步处理索引更新

## 5. 管理端功能需求

## 5.1 管理端登录

管理端需要独立入口。

要求：

* 只有具备管理端权限的用户可以访问
* 登录后根据角色加载菜单
* 未授权访问需要返回 403
* 登录状态过期需要跳转登录页

## 5.2 RBAC 权限验证

管理端使用 RBAC 做权限验证。

核心模型：

* 用户
* 角色
* 权限
* 用户角色关联
* 角色权限关联

权限建议按资源和操作拆分，例如：

* user:view
* user:update
* user:disable
* post:view
* post:update
* post:delete
* comment:view
* comment:delete
* announcement:create
* announcement:publish
* role:view
* role:create
* role:update
* role:delete
* permission:view
* audit:view

要求：

* 后端接口必须做权限校验
* 前端菜单需要根据权限动态展示
* 没有权限的按钮不展示
* 即使前端隐藏按钮，后端仍然必须校验权限
* 管理员操作需要记录审计日志

## 14. 非功能需求

### 14.1 性能

* 首页帖子列表需要分页
* 评论列表需要分页
* 热门计数可以使用 Redis 缓存
* 搜索走 Elasticsearch
* 高频事件通过 NATS 异步处理
* 图片等静态资源走 RustFS

### 14.2 可维护性

* 前后端代码需要按模块拆分
* 业务逻辑不要全部写在 handler 中
* 数据访问层与业务层分离
* 权限校验逻辑需要统一封装
* 错误响应格式需要统一
* 日志格式需要统一

### 14.3 可观测性

建议补充：

* 请求日志
* 错误日志
* 慢查询日志
* NATS 消费失败日志
